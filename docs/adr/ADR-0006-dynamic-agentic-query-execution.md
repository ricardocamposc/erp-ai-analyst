# ADR-0006 — Agentic dynamic query execution with deterministic guardrails

- **Status:** Accepted for Slice 10
- **Fecha:** 2026-08-25
- **Decision:** authorizes the implementation of Slice 10 under the defined guardrails

## Context

The catalog of specialized tools and intent paths is becoming a closed catalog of questions. A new dimension or combination of filters usually requires another tool even though the data already exists in the canonical model.

The system needs to answer new analytical queries without granting the LLM unrestricted permissions over PostgreSQL.

## Proposed decision

Adopt a dynamic query agentic workflow:

1. The LLM discovers ERP metadata through tools.
2. The analyst agent generates a plan and candidate SQL.
3. The validating agent reviews semantics, joins, and consistency.
4. A deterministic guardrail limits the query to read-only operations, tables
   authorized tables, protected sensitive columns, and operational limits.
5. PostgreSQL validates SQL using `EXPLAIN`/`PREPARE` within a transaction
   read-only; its errors return to the analyst for correction.
6. A read-only user runs only SQL approved by both layers.
7. The result is synthesized and audited.

Static tools are maintained for specialized calculations and as a migration path, but they are no longer the main limit of questions.

Tool contracts are abstracted using `ToolProvider` to enable a local implementation and a future MCP implementation.

## Alternatives considered

### Keep only static tools

Advantages: security, types, and direct ground truth.

Disadvantages: low generalization, growth per question, and overfitting to frozen evaluations.

### Execute free-form SQL generated by the LLM

Advantages: maximum flexibility and less routing code.

Disadvantages: destructive risk, improper access, incorrect joins, unpredictable cost, and poor auditability without a subsequent barrier.

### Structured plan without generated SQL

Advantages: strong validation and portability.

Disadvantages: requires a broad semantic compiler and may hide engine capabilities needed for new analysis.

## Consequences

### Positive

- New combinations of metrics and dimensions without one tool per question.
- Better demonstration of Agentic AI applied to ERP.
- Clear separation between reasoning, safety, and execution.
- Future compatibility with MCP providers.
- Auditing of SQL, decisions, and costs.

### Negative

- Greater validation and evaluation complexity.
- Syntactic correctness does not guarantee business correctness.
- A maintained semantic catalog is required.
- SQL and plans depend on the database engine.
- MCP requires an adapter and equivalence tests.

## Mandatory security

Final security cannot depend only on the LLM or the validating agent. There must be an AST parser, allowlist, read-only permissions, timeout, row limits, time limits, cost control, and auditing.

## Compatibilidad MCP

MCP should be implemented as a provider exposing metadata, validation, explanation, and read-only execution with contracts equivalent to local providers. Future adoption should change transport/configuration, not workflow semantics.

## Status

This ADR authorizes Slice 10 and supersedes, for that slice, the absolute prohibition of LLM-generated SQL in `docs/CTX.md` and ADR-0002. It does not supersede the obligations of read-only access, validation, allowlists, limits, auditing, and rejection of destructive SQL.
