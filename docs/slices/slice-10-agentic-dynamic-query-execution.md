# Slice 10 — Agentic Dynamic Query Execution

## 1. Objective

Evolve ERP AI Analyst from a closed catalog of intents and tools for predefined questions into an agentic system capable of discovering the ERP analytical model, generating dynamic SQL queries, validating them, executing them read-only, and responding with auditable evidence.

The goal is not to give the LLM unrestricted access to PostgreSQL. The goal is to let the LLM explore and combine new data within a controlled metadata, security, and operations contract.

```text
question → analyst agent → metadata + candidate SQL → validator agent
→ deterministic guardrails → read-only execution → synthesis + evidence
```

## 2. Dependencies

- Existing Slices 0–9 and runnable repository.
- Migrated and populated synthetic canonical ERP model.
- Existing FastAPI API and LangGraph workflow.
- OpenAI configured for structured outputs/tool calling.
- LangSmith available for tracing.
- ADR-0002 must be reviewed: the absolute prohibition on LLM-generated SQL will be replaced by LLM-generated SQL that is validated before execution.

## 3. Scope decision

This slice replaces production routing based on a list of questions with a dynamic query agent. It does not immediately remove static tools:

- existing static tools will be retained during migration;
- critical metrics and complex calculations may continue using specialized deterministic services;
- the dynamic agent will be the primary path for aggregations, filters, dimensions, and new combinations;
- the previous 36-case suite will remain as regression coverage, but will no longer be the only coverage evidence.

No separate agent will be implemented for each ERP domain.

## 4. Target architecture

### 4.1 Analyst agent

Responsibilities:

- interpret the business question;
- identify entity, metric, dimensions, filters, and period;
- request metadata when unknown;
- build candidate SQL;
- declare tables, columns, joins, and purpose;
- declare assumptions and ambiguities;
- never execute SQL directly.

Minimum contract:

```json
{
  "question": "...",
  "analysis_goal": "...",
  "sql": "SELECT ...",
  "tables": ["purchase_order", "supplier"],
  "columns": ["supplier.name", "purchase_order.status"],
  "joins": ["purchase_order.supplier_id = supplier.id"],
  "metrics": ["count"],
  "filters": ["status IN ('open', 'partial')"],
  "period": {"start": "<generated-from-user-intent>", "end": "<generated-from-user-intent>"},
  "assumptions": [],
  "needs_clarification": false
}
```

SQL is an artifact generated by the LLM, not an authorized instruction.

#### Required temporal semantics

The system must receive the system date on every execution; it must not contain
hardcoded historical dates. Expressions relative to the present—`this month`,
`current month`, `this year`, and `last months`—are calculated relative to
that system date, even when the ERP has no records for that period. In contrast,
`last month with sales`, `last sale`, and equivalent expressions resolve to
the last period actually available in the data. An explicit month or year must
be respected literally. A relative period with no data must never be silently
replaced by the latest historical period available.

### 4.2 Metadata tools

Tools must expose model discovery, not individual questions:

- `list_erp_tables`
- `describe_erp_table`
- `list_erp_columns`
- `list_erp_relationships`
- `list_erp_indexes`
- `get_table_row_estimate`
- `get_available_periods`
- `get_allowed_metrics`
- `get_allowed_dimensions`
- `get_data_classification`

Each response must indicate catalog version, source, timestamp, limits, and whether the information is structural or estimated. It must not return secrets or sensitive individual data by default.

### 4.3 Validator agent

Responsibilities:

- verify that the query addresses the declared goal;
- verify tables, relationships, metrics, and periods against the received catalog;
- detect incomplete or multiplicative joins;
- review aggregation, grouping, and period;
- request a correction from the analyst;
- explain the reason for rejection.

The validator agent cannot approve a query rejected by the security layer or by
the ERP's actual validation.

### 4.4 Deterministic security layer

It must always run, even when a validator agent exists:

- parse SQL through an AST;
- allow only `SELECT` and controlled read-only CTEs;
- block `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `DROP`, `ALTER`, `TRUNCATE`, `CREATE`, `GRANT`, `COPY`, write functions, and multiple statements;
- allow only tables from the authorized catalog and block sensitive columns;
- retain the sensitive-column allowlist as an access boundary without
  replacing validation of the ERP's SQL dialect;
- block system tables, secrets, and sensitive columns;
- require temporal filters on large transactional tables;
- limit time range, tables, joins, rows, bytes, and timeout;
- run `EXPLAIN`/`PREPARE` in a read-only transaction so PostgreSQL
  validates syntax, columns, types, aliases, joins, and `GROUP BY`;
- reject excessive cardinality or cost;
- run with a PostgreSQL user without write permissions;
- record normalized SQL, hash, decision, and reason.

Resultado estructurado:

```json
{
  "status": "approved|rejected|needs_revision",
  "normalized_sql": "...",
  "reasons": [],
  "estimated_rows": 120,
  "estimated_cost": "...",
  "tables": ["purchase_order"],
  "columns": ["status"],
  "limits_applied": ["max_rows", "read_only_role"]
}
```

### 4.5 Executor

The executor receives approved queries only:

- read-only connection;
- timeout and cancellation;
- columns, rows, types, and metadata;
- explicit limits without silent truncation;
- distinction between zero rows and an error;
- period, SQL hash, row count, and timestamp;
- never execute a query without current approval.

### 4.6 Synthesizer

It receives results and evidence only. It must preserve numbers, distinguish facts from recommendations, declare insufficiency, avoid unsupported causation, and retain the complete query in the audit record even when it does not always show it to the user.

### 4.7 Coordinator agent

The workflow must have an explicit coordinator. It is responsible for:

- receive the question and create the `request_id`;
- maintain the shared investigation state;
- decide which agent should run next;
- provide metadata and validator diagnostics to the analyst;
- wait for each agent's response before proceeding;
- limit iterations and prevent cycles;
- send approved queries only to the executor;
- gather results, evidence, warnings, and audit data;
- provide the final context to the synthesizer;
- respond to the API with a stable contract.

The coordinator will be a LangGraph workflow. No direct, unobservable
communication between agents will be implemented: all communication will pass
through typed state, events, and messages with `request_id`, `stage`, `attempt`,
`status`, and validated payload.

### 4.8 Agent communication

The minimum internal messages will be:

- `AnalysisRequest` — question, conversation, permissions, and limits;
- `MetadataRequest` / `MetadataResponse`;
- `QueryProposal` — goal, candidate SQL, metadata used, and assumptions;
- `ValidationRequest` / `ValidationResponse`;
- `RevisionRequest` — errors and required corrections;
- `ExecutionRequest` / `ExecutionResponse`;
- `SynthesisRequest` / `SynthesisResponse`;
- `WorkflowCompletion`.

Each message will have a Pydantic schema, contract version, and explicit terminal
state. An agent may not consume another agent's raw output without schema
validation.

## 5. ERP semantic model

Create a versioned catalog with:

- tables, columns, and types;
- primary and foreign keys;
- permitted relationships;
- temporal columns;
- metrics and formulas;
- groupable dimensions;
- valid filters;
- data sensitivity;
- indexes and approximate cardinality;
- business synonyms and labels;
- functional domain.

The catalog must separate structural metadata, business semantics, permissions, and operational limits. The LLM may receive it through tools, but must not discover critical business conventions on its own.

## 5.1 Mandatory contract for ERP providers

Every ERP that wants to connect must implement the same abstract contract,
`ERPQueryProvider`. This slice's local provider will be the reference
implementation. At minimum, it must provide:

| Capability | Mandatory tool/operation |
|---|---|
| Authorized tables | `list_erp_tables` |
| Table schema | `describe_erp_table` |
| Columns | `list_erp_columns` |
| Relationships | `list_erp_relationships` |
| Indexes | `list_erp_indexes` |
| Cardinality | `get_table_row_estimate` |
| Periods | `get_available_periods` |
| Metrics | `get_allowed_metrics` |
| Dimensions | `get_allowed_dimensions` |
| Sensitivity | `get_data_classification` |
| Validation | `validate_query` |
| Plan/cost | `explain_query` |
| Read | `execute_readonly_query` |

The contract must also define SQL dialect, pagination, maximum limits, timeouts,
normalized errors, data types, catalog version, and evidence. A connector that
cannot implement a capability must declare it as `unsupported`, never simulate it.

Static business tools are not the minimum integration contract. They are
optional optimizations that a provider may offer when they add a specialized
metric.

## 6. Correction cycle

1. Analista genera plan y SQL.
2. LLM validator reviews semantics.
3. Local guardrail reviews only security and limits.
4. PostgreSQL ejecuta `EXPLAIN`/`PREPARE` en read-only.
5. If PostgreSQL returns an error, the coordinator sends it to the LLM analyst.
6. At most three complete revisions are allowed.
7. Only SQL approved by security and PostgreSQL may be executed.
8. If there is no approval, respond with `insufficient_data`, `needs_clarification`, or `unsafe_query` without executing.

An indefinite cycle is not allowed.

## 7. Auditing and observability

Create `analysis_interactions` with:

- `request_id`, `conversation_id` y timestamp;
- original question;
- structured goal/intent;
- semantic-model version;
- agent and model;
- SQL candidato y hash;
- validator and guardrail decisions;
- SQL normalizado ejecutado;
- tables and columns;
- filas estimadas y reales;
- latency by stage;
- status, response, warnings, and errors;
- tokens/cost when available.

Do not store chain-of-thought. Store decisions, technical artifacts, summaries, and evidence required for auditing.

Auditing must identify questions without metrics, rejected queries, clarification requests, expensive queries, missing columns, join errors, and new recurring needs.

## 8. Future MCP compatibility

Decouple the workflow from the local implementation through a `ToolProvider` interface for metadata, validation, estimation, execution, and evidence.

```text
Workflow LangGraph
        ↓
ToolProvider
        ├── LocalProvider → PostgreSQL local
        └── MCPProvider   → MCP server / ERP externo
```

The replacement will not literally require zero changes: the MCP client must be implemented, authentication and errors mapped, schemas verified, guardrails and auditing preserved, and the location of final validation decided. The goal is to limit changes to the provider and configuration rather than prompts or one tool per question.

Tools MCP recomendadas:

- `metadata.list_tables`
- `metadata.describe_table`
- `metadata.list_relationships`
- `metadata.list_indexes`
- `query.validate`
- `query.explain`
- `query.execute_readonly`

The security policy must exist on both client and server when an external ERP is connected.

## 9. Migration

### Phase A — contracts and catalog

- freeze the initial semantic catalog;
- define the SQL-plan schema;
- define parser/validator and limits;
- add auditing;
- keep the current path as a fallback.

### Phase B — metadata

- implement discovery of tables, fields, relationships, and indexes;
- add allowlist and tests;
- expose cardinality and periods.

### Phase C — generation and validation

- add analyst agent;
- add validator agent;
- implement limited correction;
- implement deterministic guardrails;
- test exclusively SELECT over synthetic data.

### Phase D — execution and synthesis

- execute approved SQL only;
- return typed evidence and results;
- record auditing;
- compare dynamic results against independent ground truth.

### Phase E — adoption

- migrate simple purchases, sales, and inventory queries;
- compare static and dynamic paths;
- migrate cross-domain queries;
- retain specialized tools for complex metrics;
- retire static paths only with sufficient evidence.

## 10. Evaluation

Evaluation must measure more than exact tool matching:

- valid SQL;
- correct intent, tables, columns, and joins;
- filtros temporales correctos;
- calculation against independent ground truth;
- sufficient evidence;
- rejection of dangerous SQL, sensitive tables, and expensive queries;
- correct clarification rate;
- estimated versus actual cardinality;
- latencia, coste y estabilidad entre reformulaciones;
- new questions outside the original dataset.

Minimum cases:

- 50 new purchasing questions;
- 50 new sales questions;
- 50 new inventory questions;
- dimensiones, filtros y periodos variados;
- zero results;
- nonexistent columns;
- SQL destructivo;
- rango excesivo;
- query without a temporal filter;
- sensitive table;
- high cardinality;
- ambiguity requiring clarification.

The current Agentic v2 suite is retained as historical regression coverage, but it will not be the only generalization metric.

## 11. Security and privacy

- only synthetic data in the repository;
- read-only user;
- no secrets in prompts, metadata, or logs;
- table/column allowlist;
- sensitive-data classification;
- masked samples;
- access auditing;
- the LLM does not change permissions, schema, or configuration;
- rejection of sensitive individual payroll data.

## 12. Out of scope

- ERP writes;
- journal-entry generation or accounting modifications;
- SQL multi-statement;
- schema administration;
- access to uncatalogued tables;
- real MCP connectors in this first implementation;
- immediate replacement of all deterministic tools;
- production claims without equivalent operational evidence.

## 14. Acceptance criteria

1. An unanticipated question generates a structured SQL plan without a new dedicated tool.
2. The agent discovers tables, fields, and relationships through metadata tools.
3. The validator corrects an invalid column or relationship within the iteration limit.
4. No destructive SQL reaches the executor.
5. No unbounded query consumes unlimited resources.
6. Queries with nonexistent fields or invalid joins are explicitly rejected or corrected.
7. The executor uses read-only access and a timeout.
8. Each execution produces an SQL hash, evidence, row count, and audit record.
9. The response distinguishes zero results, insufficient data, rejection, and technical error.
10. The dynamic path answers new questions from at least three domains without creating tools per question.
11. Static tools continue working during migration.
12. A `ToolProvider` later enables an MCP provider without changing the business workflow.
13. The suite covers destructive commands, disallowed tables, excessive ranges, high cardinality, and sensitive columns.
14. Evaluation compares dynamic results with independent ground truth.
15. The coordinator explicitly runs and waits for analyst, validator, guardrail, executor, and synthesizer responses through typed state.
16. Each agent has a single responsibility and its messages are traced with `request_id` and contract version.
17. The local provider implements all mandatory operations in the `ERPQueryProvider` contract.
18. A fake/test provider implementing the same contract can replace the local provider without changing agents or the coordinator.
19. A future MCP provider can expose the same operations without changing the message contract or public API response.
20. The frontend consumes `POST /api/v1/dynamic-analysis`, preserves the
    `conversation_id`, and presents the response, evidence, guardrail status,
    validated SQL, row count, and query hash.

## 15. Risks and mitigations

- Valid but business-incorrect SQL → semantic catalog and independent ground truth.
- Joins that duplicate amounts → permitted relationships and cardinality validation.
- Ambiguous metrics → versioned metric definitions and clarification.
- Inaccurate estimated cardinality → `EXPLAIN`, strict limits, and timeout.
- Prompt injection in metadata or data → treat metadata/results as untrusted data.
- Sensitive columns → classification and allowlist.
- Local/MCP divergence → `ToolProvider` contract and equivalence tests.

## 16. Definition of Done

A third party can ask an analytical question not included in the dataset, observe how the system discovers the model, inspect the candidate SQL, verify its validation, confirm that it ran only after the guardrails, and receive an evidence-backed response through the frontend. The same contract can be implemented with a local or MCP provider without rewriting the workflow.

## 17. Prohibitions

- Do not reintroduce a question dictionary to fake generalization.
- Do not allow free-form SQL without a parser, read-only permissions, and limits.
- Do not rely only on the validator agent for security.
- Do not create a static tool for every question during this slice.
- Do not claim full MCP compatibility until the real provider is tested.
- Do not remove ground truth or replace it with subjective LLM evaluation.
